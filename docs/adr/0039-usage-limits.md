# 39. Traffic quotas and usage limits

- **Status:** Accepted (built 2026-10-22, tested with the fake only)
- **Date:** 2026-10-22

## Context

Packages and servers have carried a monthly traffic quota (`traffic_bytes`) since Phase 1, but nothing counted traffic, so the quota was never enforced. Providers also need to act on servers that keep a node busy: a VPS that runs at full CPU, saturates its port or hammers the disks for hours slows down every neighbour on the node. Virtualizor and VirtFusion both suspend servers over their bandwidth and can act on abusive ones.

The live figures of ADR 0036 are sampled only while an administrator watches a server page, so they cannot be used for accounting.

## Decision

1. **Collection.** `usage:collect` runs every 5 minutes (`UsageCollector`). It reads `GET /cluster/resources?type=vm` once per active cluster, the request the sync already makes, which lists `cpu`, `mem`, `maxmem`, `netin`, `netout`, `diskread`, `diskwrite` and `uptime` of every VM. Nothing is asked per server. Servers that are active or suspended and whose VMID the cluster lists get one row in `usage_samples`: CPU and memory in per cent, network and disk rates in bytes per second. The rates come from the counters of the previous run, kept on the server (`servers.usage_counters`). Samples are pruned after 48 hours. A cluster that does not answer is skipped for that run.
2. **Counters reset when the VM process restarts** (a restart, a move to another node). When `uptime` went down or a counter went down, the new value is counted from zero; what happened between the previous run and the restart (at most 5 minutes) is lost. The first run after a server is created or adopted counts nothing.
3. **Traffic periods.** Traffic is summed per server and month in `traffic_periods` (`period_start`, `in_bytes`, `out_bytes`). A month starts on the *traffic reset day* (1–28, default 1) at midnight in the panel's time zone. What counts against the quota is set on *Panel settings*: incoming and outgoing together (default), outgoing only or incoming only. Changing the reset day starts new periods; the old rows stay.
4. **Traffic quota.** When a server's counted traffic reaches its quota (`traffic_bytes`, null = unlimited), a `usage_violations` row of kind `traffic` is opened for the period, and the *traffic quota action* runs: `none` (only recorded) or `suspend`. Both settings default to doing nothing beyond recording (`PROXMOTION_TRAFFIC_OVERRUN_ACTION=none`), so an upgrade never suspends servers on its own.
5. **Usage limits.** Optional thresholds on *Panel settings*: CPU (% of the server's vCPUs), memory (% of its memory), disk I/O (read + write, MB/s) and network (in + out, Mbps), and one *time window* (15–1440 minutes, default 60). A limit is exceeded when the average of the samples within the window is at or above it and the samples cover at least 80% of the window. Then a violation of that kind is opened and the *usage limit action* runs: `none`, `stop` (forced power-off; the customer may start the server again) or `suspend`. An open violation is resolved once the average falls below the limit again. Every limit is off until a value is entered.
6. **One action per violation.** An action is taken once, when its violation opens (or at the next run when a task was still running). An administrator or billing system that unsuspends a server suspended over its traffic quota lets it run for the rest of the period: its violation stays open and acted on.
7. **Who suspended a server.** `servers.suspension_cause` is `traffic` or `usage` for a suspension started by the panel, null otherwise; `suspension_reason` says why in English (e.g. *Traffic quota exceeded: 101 GB of 100 GB.*). Unsuspending clears both. A server suspended over its traffic quota is **unsuspended by the panel** once it no longer exceeds it: a new period started, or its quota was raised. A server suspended over a usage limit stays suspended until an administrator or the billing system unsuspends it.
8. **Billing systems take over automatic suspensions.** `POST /servers/{id}/suspend` on a server the panel suspended for usage answers `200` with the server and makes the suspension the billing system's (cause cleared, its reason stored), so a server suspended for non-payment is never unsuspended at the next period. The WHMCS and WISECP modules call it also when the server is already suspended with a `suspension_cause`. The API's server gains `suspension_cause` and `traffic` (the current period, bytes in and out, bytes counted); the suspensions themselves reach billing systems as the usual `server.suspended` / `server.unsuspended` webhooks, and a new event `server.usage_exceeded` is sent when a violation opens, whatever the action.
9. **Exemptions.** *Exempt from usage limits* on the server page (audited as `server.usage_exempt_changed`) records violations but never acts on them, e.g. for a customer who pays for dedicated CPU. Test servers are not exempt.
10. **Audit and visibility.** Actions are audited as `server.usage_action` (no user, no token). The server page shows the traffic of the period against the quota, open and recent violations, and why the server was suspended. The dashboard lists servers with open violations.

## Consequences

- The quota stored on packages and servers is enforced once administrators choose `suspend`. Throttling instead of suspending (lowering `rate=` of `net0`) is left for later.
- The 5-minute samples are averages of instants: Proxmox's `cpu` and `mem` are the current values, not averages over 5 minutes. A window of 12 samples smooths that, but a short window can miss or exaggerate spikes. Disk and network rates are true averages from the counters.
- Memory as Proxmox reports it is the guest's view only with the balloon driver; otherwise it is the QEMU process's memory, which grows to the VM's size and stays there. The memory limit is therefore off by default and documented as such.
- About 290 sample rows per server per day; pruned hourly after 48 hours.
- Not verified on a real Proxmox: the fields and units of `/cluster/resources` for VMs (`netin` = bytes the guest received), counters after a live migration, and the `cpu` value relative to the VM's vCPUs. Traffic graphs remain Phase 6 work. The billing modules show the month's traffic (WHMCS client area and `UsageUpdate` into its usage statistics, WISECP's bandwidth gauge), built 2026-10-22 and tested with the billing systems faked.
