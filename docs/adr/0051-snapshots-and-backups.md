# 51. Snapshots and backups

- **Status:** Accepted (phase 1, snapshots, built 2026-10-28; phase 2, manual backups and restore, built 2026-10-29; schedules not built)
- **Date:** 2026-10-28

## Context

Phase 7 of the roadmap: customers and administrators need to take a server back to an earlier state. Virtualizor and VirtFusion offer both kinds:

- **Snapshots** live on the VM's own storage. They are quick, cheap to take and quick to roll back, but they die with the disk: a failed storage, a reinstall or a termination takes them along. They are an "undo" before risky changes, not a backup.
- **Backups** (Proxmox `vzdump`, to a backup storage or a Proxmox Backup Server) are full copies on other storage. They survive the VM and can be restored after a reinstall, but they take minutes to hours and room on the backup storage.

What exists today:

- Packages have `snapshot_slots` and `backup_slots` (0–100, default 0) since Phase 1. The admin form edits them; nothing reads them, they are not copied to servers and the API does not show them.
- ADR 0037 refuses to move a server with snapshots (a `parent` key in its config) and leaves their handling to this phase.
- *Reset after trial* (ADR 0018 §7) reinstalls a test server from its template "until snapshots exist".
- The panel has no `Snapshot` or `Backup` model and asks for neither `VM.Snapshot` nor `VM.Backup`. `AGENTS.md` lists both models and a `Domain/Backups/` folder as planned.

Constraints that shape the design:

- **Pool-limited tokens** (Phase 2: the token has VM rights on the cluster's resource pool only, and the permission check reports excess privileges). Proxmox's own scheduled backup jobs (`/cluster/backup`) need `Sys.Modify` on `/`, which the permission check calls dangerous. They also cannot carry a quota per server, nor tell the panel when a backup ended.
- **The panel is the source of truth** (§3.3.6). Restored or rolled-back VMs bring back the configuration of their time: old resources, old firewall, old addresses inside the guest. The panel must bring them back in line.
- **Cloud-init identity** (ADR 0011, 0012). Changing cloud-init fields (`ipconfig0`, `name`, `sshkeys`, `cipassword`) makes cloud-init see a new instance and regenerate SSH host keys. A restore must not change them.
- **Staged tasks** (ADR 0032). Backups and restores take long; no worker may sleep through them.

## Decision

### 1. Two features, built in phases

1. **Snapshots:** admin, API, WHMCS, WISECP.
2. **Manual backups and restore:** the same surfaces.
3. **Scheduled backups and retention.**
4. **Later, not in this ADR:** file-level restore from Proxmox Backup Server, downloads of backup files, backups to storage outside Proxmox.

Each phase is usable on its own and gets its own entry in `AGENTS.md`.

### 2. Limits per package, copied to servers

- `snapshot_slots` becomes the most snapshots a server may have; `backup_slots` the most backups. 0 turns the feature off for the server.
- Both are copied to the server on creation and resource changes like the other resources (`servers.snapshot_slots`, `servers.backup_slots`). Custom servers set them by hand, and billing systems send them in `resources`.
- WHMCS configurable options `snapshots` and `backups` add to the package, like `extra_ipv4`.
- The API shows both in `resources` and in `GET /packages`.
- A migration copies the package values to existing servers. Packages keep their current values (default 0), so an upgrade turns nothing on.
- Lowering a limit never deletes anything. The server just cannot take new ones until it is under the limit again.

### 3. Snapshots

- **Taking one:** `POST /nodes/{node}/qemu/{vmid}/snapshot` with:
  - `snapname`: generated by the panel as `pmx` plus a base-36 timestamp, which fits Proxmox's rules (letter first, `[A-Za-z0-9_-]`, at most 40 characters).
  - `description`: the customer's label (at most 64 printable characters, validated, never put into a shell).
  - `vmstate=0`: disk and configuration only, no RAM. RAM state would put the guest's memory, often several GB, on the VM storage, and resuming a running state after a rollback surprises customers.

  Proxmox freezes the guest's file systems through the agent while it takes the snapshot (to verify).
- **Storage support:** only storages that support snapshots (LVM-thin, ZFS, Ceph RBD, qcow2 on directory, NFS or CIFS storage) can hold them. The panel knows a storage's type from the sync. For a server on other storage (plain LVM, raw on a directory), `POST` answers `422` `snapshots_not_supported`, and the limit is shown as 0 with the reason.
- **Rollback:** `POST …/snapshot/{snapname}/rollback`. A snapshot without RAM leaves the VM stopped (to verify); the panel starts it again when it was running. Then it re-applies the panel's state (§5).
- **Deleting:** `DELETE …/snapshot/{snapname}`.
- **Tasks:** each is a task (`create_snapshot`, `rollback_snapshot`, `delete_snapshot`), audited.
  - Rollback is destructive. The admin UI asks to type the hostname; the billing modules ask for confirmation.
- **Model:** `Snapshot` (uuid, server, Proxmox name, label, `created_at`, task).
  - The page lists the panel's rows and marks rows Proxmox no longer has (read from `GET …/snapshot` when the list is shown).
  - Snapshots made outside the panel are shown to administrators as drift (ADR 0005), never listed to customers, and never deleted.
- **Interactions:**
  - **Reinstall and terminate** delete the VM and its snapshots with it. The confirmation says so, and the rows are removed.
  - **Moves** stay refused while snapshots exist (ADR 0037). The dialog offers to delete them first.
  - **Disk growth** (upgrades, `ResourceChanger`) is refused with `409` `snapshots_exist` while snapshots exist, until resizing a disk with snapshots is verified per storage type. CPU and memory changes are allowed.
  - **Test servers:** *Reset after trial* rolls back to a snapshot labelled `trial base` when the server has one, otherwise reinstalls as today.

### 4. Backups

- **Backup storage:** administrators tick *Use for backups* on storages whose content includes `backup` (a directory, NFS or CIFS storage, or Proxmox Backup Server), next to *Use for servers*. A backup goes to the ticked storage of the server's cluster with the most free room that the server's node can reach (shared, or the node's own). A server whose cluster has none cannot take backups (`422` `no_backup_storage`).
- **Taking one:** `POST /nodes/{node}/vzdump` with:
  - `vmid`, `storage`, `mode=snapshot` (the VM keeps running; the guest is frozen through the agent);
  - `compress=zstd` (ignored by Proxmox Backup Server), `remove=0` (the panel prunes, §6);
  - `notes-template` with the hostname and the server's uuid, so a backup can be told apart on the storage.

  The result is found by listing `GET /nodes/{node}/storage/{storage}/content?content=backup&vmid=` after the task. The task is staged: start vzdump, then wait for the UPID in stages (ADR 0032), with its own deadline (6 hours, set on *Panel settings*). Proxmox locks the VM while it runs, so the server counts as busy and other tasks answer `409`. Administrators can cancel a running backup, which stops the Proxmox task.
- **Model:** `Backup`. Its fields:
  - uuid, server, cluster, storage;
  - Proxmox volume id;
  - kind `manual` or `scheduled`, and the customer's label for manual ones;
  - status `creating`, `available`, `failed`, `deleting` or `missing`;
  - size in bytes;
  - the OS template, hostname and disk size at the time;
  - the task, and `created_at` / `finished_at`.
- **Restoring** (`restore_backup`, staged, destructive, confirmed like a reinstall):
  1. Stop the VM (forced after the usual shutdown timeout).
  2. `POST /nodes/{node}/qemu` with `vmid` (the server's), `archive` (the volume id), `force=1` (replace the VM), `storage` (the server's disk storage) and `unique=0` (keep the MAC).
  3. Re-apply the panel's state (§5) and start the VM.
  4. The server's OS template becomes the backup's, since the guest's system is now the one of the backup.

  Restoring is only possible on the cluster that has the backup's storage. A server moved to another cluster sees its older backups as not restorable (with the reason) until they are deleted or age out.
- **Deleting:** `DELETE /nodes/{node}/storage/{storage}/content/{volume}` as a short task, audited.
- **Survival:** backups survive reinstalls (that is their point), and restoring one after a reinstall is allowed. On termination they are deleted, unless *Keep backups of terminated servers* (*Panel settings*, days, default 0) keeps them. Then a daily job deletes them afterwards, and administrators can restore one by adopting the VM again (out of scope here: they stay listed under the terminated server).

### 5. Re-applying the panel's state after a rollback or restore

A rollback or restore brings back the VM configuration of its time. The panel writes back what it owns, but never a cloud-init field:

- **Proxmox configuration:** `cores`, `memory`, the CPU and disk limits (ADR 0034), `net0` with the current MAC, `rate=` and `firewall=1`.
- **Disk:** grown to the server's current `disk_mib` when the restored disk is smaller, followed by the `disk_resized` guest script.
- **Firewall:** options, the anti-spoofing IP set, the isolation sets and the panel's rules, as `apply_firewall` writes them (ADR 0033–0035).
- **Inside the guest**, once the agent answers:
  - the `addresses_changed` script with the current addresses (they may have changed since, ADR 0011, 0028);
  - `hostname_changed` when the name differs;
  - `ssh_keys_changed` with the panel's keys (ADR 0049).

`ipconfig0`, `name`, `sshkeys`, `cipassword` and `ciuser` stay as restored. They are the values of the server's creation or last reinstall in both the backup and the current config, unless the backup is older than the last reinstall. In that case cloud-init sees the identity of that older install, which is what the customer restored.

The root password inside the guest is the one of the backup's time. The panel forgets the password it stored (`root_password` cleared, `GET /servers/{id}/password` answers `410`), and billing systems offer *reset password* as usual. The server is checked from inside afterwards (`ServerVerifier`, ADR 0032 §6).

### 6. Scheduled backups and retention (phase 3)

- **Schedule:** a package or server sets `backup_schedule`: `none` (default), `daily` or `weekly`.
- **Queuing:** `backups:schedule` runs every 10 minutes during the *backup window* of *Panel settings* (default 01:00–06:00 in the panel's time zone). It queues the servers that are due, spread by their id across the window.
- **Concurrency:** at most *Backups at once per node* (default 1) and per storage (default 2) run at a time. A server that is busy is tried again at the next run, and skipped for the day when the window ends.
- **Retention:** a successful scheduled backup deletes the oldest scheduled backups beyond the server's `backup_slots`. Manual backups count against the same slots but are never deleted automatically: a manual backup is refused (`409` `backup_slots_full`) while the slots are full, and the customer deletes one first. A server whose manual backups fill every slot gets no scheduled backups, and its page says so.
- **Notifications:** a failed scheduled backup notifies administrators (ADR 0044, new event `backup_failed`) and sends the usual `task.failed` webhook.

### 7. API, webhooks and billing modules

- **Snapshots:**
  - `GET /servers/{id}/snapshots` (`servers:read`);
  - `POST /servers/{id}/snapshots` with `label`;
  - `POST …/snapshots/{snapshot}/rollback`;
  - `DELETE …/snapshots/{snapshot}`.

  Writes need `servers:write`, are idempotent and answer `202` with the task.
- **Backups:**
  - `GET /servers/{id}/backups`;
  - `POST /servers/{id}/backups` with `label`;
  - `POST …/backups/{backup}/restore`;
  - `DELETE …/backups/{backup}`.

  The same scopes and answers as snapshots. A list item gives kind, label, status, size, OS template name and times, never the volume id or the storage.
- **Webhooks:** the new task types arrive through `task.succeeded` / `task.failed`. `server.restored` is sent after a successful rollback or restore, so billing modules can refresh the password state.
- **Billing modules:** WHMCS gets *Snapshots* and *Backups* sections in the client area, and WISECP gets tools. Each lists the items with take, roll back or restore, and delete, with confirmations.
- **Admin:** a *Backups* tab on the server page with both lists, the actions, the schedule and the slots.
- **Isolation:** every endpoint gets scope, isolation and contract tests like the others.

### 8. Permissions

The permission check asks for:

- `VM.Snapshot` and `VM.Snapshot.Rollback` on the pool;
- `VM.Backup` on the pool;
- `Datastore.AllocateSpace` and `Datastore.Audit` on each *Use for backups* storage.

A restore over an existing VM may need more (`VM.Allocate` on the VMID, or on `/vms` for `force=1`); this is to verify before phase 2. Nothing on `/` beyond today's read privileges: no `Sys.Modify`, since the panel schedules backups itself (Context).

## Consequences

- **Space nobody accounts for:** snapshots use room on the VM storage that placement does not count. Storage health (ADR 0047) shows it, and `snapshot_slots` bounds it per server. Over-commit ratios should leave room for them.
- **Busy servers:** a backup blocks a server's other operations for its duration, as Proxmox's lock would anyway. Long backups of large servers in the window are the cost of `mode=snapshot` without Proxmox's own scheduler.
- **Restored state:** a restore brings back the guest's passwords, users and software of its time. Only the network, hostname and the panel's SSH keys are brought up to date.
- **No duplicate jobs:** the panel's scheduler duplicates part of Proxmox's backup jobs, but keeps the token pool-limited and gives per-server quotas and webhooks.

**To verify on a real Proxmox** (PVE 8.x and 9.x, pool-limited token) before each phase:

- Snapshots on each storage type, with guest agent freeze. The VM's state after a rollback without RAM.
- `PUT …/resize` of a disk with snapshots per storage type.
- `vzdump` with `mode=snapshot` and the agent, and the volume id found through the storage content.
- A restore with `force=1` and `unique=0` keeping the MAC; the privileges it needs.
- Whether vzdump includes the VM's firewall file and the cloud-init drive.
- What cloud-init does after a restore of an unchanged config.
- Proxmox Backup Server as a storage.

## Phase 1 as built (2026-10-28)

Snapshots are built as decided above, with these details settled while building them. Tested with the faked Proxmox and billing systems only.

- **The list is the panel's rows.** Reading Proxmox's snapshots on every page view would put a Proxmox call into HTTP requests. A snapshot deleted in Proxmox is noticed when it is deleted through the panel (nothing left to delete counts as done) or rolled back to (the task fails with Proxmox's message). Snapshots made outside the panel are not listed, nor reported as drift yet (§3 planned that; left for later).
- **Storage types** that take snapshots: `lvmthin`, `zfspool`, `rbd`, and `dir`, `nfs`, `cifs` (Proxmox itself refuses raw files there). A server without a recorded storage (adopted) may try; Proxmox decides.
- **Status:** taking and rolling back need an active server; deleting also works while it is suspended.
- **Snapshot tasks are not staged.** They wait for Proxmox like power actions (up to 30 minutes per Proxmox task). Backups (phase 2) stay staged as §4 says.
- **After a rollback** (§5): `VmState` (shared with resource changes) writes resources, port speed, the disk size and the firewall with exactly the server's addresses. The guest's addresses, hostname and SSH keys go back in with the `addresses_changed`, `hostname_changed` and `ssh_keys_changed` scripts (`GuestRefresh`) when the server starts: at once when it ran (the rollback starts it again), else at its first start through the panel (*Start*, *Reboot*, *Unsuspend*; `servers.guest_refresh_pending`, cleared once the address script ran), so a server its owner stopped stays stopped. A failing SSH key script leaves a note instead of failing the rollback or the start. Starts outside the panel (in Proxmox) miss the refresh; *Apply again* on the server page covers the addresses then. Apps installed after the snapshot are marked removed, and the stored root password is cleared. A rollback is refused while an app script is queued or running on the server (`AppInstallations::scriptRunning()`, shared with moves): app scripts run outside the server's tasks, and the rollback would take the disk away under them.
- **Admin:** a *Snapshots* tab on the server page; it becomes *Backups* (with both lists) in phase 2. The custom create form and *Change resources* have the two slot fields.
- **Billing:** WHMCS configurable options `snapshots` / `backups` set the slots and `extra_snapshots` / `extra_backups` add to the package's, like the other resources; WISECP takes the `extra_…` add-on values.

## Phase 2 as built (2026-10-29)

Manual backups and restore are built as decided in §4, with these details settled while building them. Tested with the faked Proxmox and billing systems only.

- **Choosing the storage:** storages are synced once per node, shared ones included, so the server's node's own rows are the storages it reaches. Of those ticked *Use for backups*, available and taking content `backup`, the one with the most free room wins. It is chosen when the backup is requested and kept on the task. The flag can only be ticked on storages with content `backup`.
- **Rows only for backups Proxmox has,** as for snapshots: the `creating`, `failed`, `deleting` and `missing` statuses of §4 are not stored. A running backup is its task, and a failed one leaves only its failed task. The row is written once vzdump has finished and its volume is found in the storage's content: by the backup's uuid, which goes into its notes (`notes-template`), else as the newest volume of the VM since the task started that no row records. A backup deleted outside the panel is noticed when it is deleted (nothing left counts as done) or restored (the task fails with Proxmox's message).
- **`create_backup`** is staged with the deadline `backup_deadline_minutes` on *Panel settings* (default 360, `PROXMOTION_BACKUP_DEADLINE_MINUTES`). It waits between runs while another task holds the VM, and checks the vzdump task every 60 seconds. `compress=zstd` is left out for Proxmox Backup Server storages. The row records the VMID the backup was taken of, by which the storage is listed later (a move to another cluster may change the server's). Administrators can stop a running backup from the task list, like their script runs (`TaskFailer::cancel()`): the task fails at once, and `StopProxmoxTask` stops the vzdump task (`DELETE /nodes/{node}/tasks/{upid}`) so its lock is released. Once vzdump has finished, the task can no longer be cancelled: it only records the backup, which would otherwise stay unlisted on the storage. A cancel that lands while vzdump is being started finds no task to stop; the stage stops it itself once Proxmox has answered, then ends.
- **`restore_backup`** is staged with the same deadline. Its stages:
  1. **stop:** wait between runs while another task holds the VM, remember whether it ran, then stop it. A VM without a configuration (an earlier restore failed after Proxmox deleted it) is restored from scratch.
  2. **restore:** `POST /nodes/{node}/qemu` with `archive`, `force=1`, `unique=0` and the server's storage. No `pool` over an existing VM: a restore over the existing VMID is believed to keep the pool membership, which needs checking. A VM restored from scratch gets the cluster's resource pool. The VM's snapshots go with its disks, so their rows are dropped.
  3. **configure, resize, firewall:** `VmState` as after a rollback, and the VM's notes and tags written again (`VmLabels`), since the backup brings back those of its time. The disk grows in a stage of its own, checked between runs like a creation's.
  4. **start, wait for the agent, refresh the guest, verify:** only when it ran. **Unlike §4**, a server that was stopped stays stopped and gets its addresses, hostname and SSH keys at its first start through the panel, as after a rollback (phase 1).

  The server's OS template becomes the backup's. Apps installed since the backup are marked removed, and the stored root password is cleared. A restore is refused while an app script runs, as a rollback is. A failed restore leaves the server `active`, not `error`, with the failed task and Proxmox's message. The customer can try again, restore another backup or reinstall. A server that runs again is checked from inside afterwards (`ServerVerifier`), as after a creation, without failing the restore; the earlier checks are dropped in any case, since they describe the disk before the restore.
- **Restorable:** a backup is restorable while it is on the server's cluster and the server's node has a storage of that name that is shared, or the backup was taken on that node. Otherwise it is listed with `restorable: false` and the reason, and a restore answers `409` `backup_not_restorable`.
- **`delete_backup`** goes through the backup's own cluster and the node it was taken on. When that node is gone, it uses a node with a shared storage of that name; a storage that is not shared is refused, since another node's storage of the same name is a different one.
- **Termination** queues a job per backup (`DeleteBackupVolume`) that deletes its volume and row, so the termination does not wait for every backup in one run. A backup that cannot be deleted never stops the termination: its job tries three times, five minutes apart, then logs a warning and keeps the row under the terminated server, so it can be found and removed by hand. *Keep backups of terminated servers* (§4) is left for phase 3, which adds the daily job that would delete them later.
- **API:** `GET /servers/{id}/backups` gives kind, label, size, OS template name, time and `restorable` with `unrestorable_reason`, never the storage or the volume. Refusals answer `422` `backups_not_supported` / `no_backup_storage`, `409` `backup_slots_full` / `backup_not_restorable`.
- **Admin:** the server page's tab is now *Backups*, with the snapshots above the backups. Admins also see the storage of each backup and where the next one goes. The cluster page has a *Use for backups* column.
- **Permissions:** `VM.Backup` is added to the pool's privileges (it is in `PVEVMAdmin`). `Datastore.AllocateSpace` on `/storage` and `Datastore.Audit` on `/` were already required. What a restore with `force=1` needs is still to verify (§8).

## Answered questions

Settled by the maintainers on 2026-10-28, as the draft proposed:

1. **No RAM state in snapshots** (`vmstate=0` always), also not for administrators.
2. **Backups belong to one server:** they cannot be restored into another server, not even one of the same customer.
3. **No downloads** of backup files.
4. **Backups of terminated servers are deleted at once** by default (*Keep backups of terminated servers* = 0 days).
5. **Snapshots first** (phase 1), then manual backups and restore (phase 2), then schedules and retention (phase 3).
